# ADR-0016 跨语言候选：打中文时候选栏直接出目标语言

- 状态：已采纳
- 日期：2026-11-25
- 相关：ADR-0015（语言选择与 app mode）、`crates/gloss`、`crates/engine::Session`

## 背景

用户的原话是要「输入汉语的同时，候选直接出英语或者我选定的语言」。在此之前，仓库里已经有三样东西，但都不是这个：

| 已有 | 位置 | 实际行为 | 差在哪 |
|---|---|---|---|
| `liana_translate` | `crates/ffi` → `crates/gloss` | 把**已上屏**的中文整句翻成 7 种语言的一行 | 要先上屏、要再点一次；100 条对照表覆盖不住日常用词 |
| `en-glossary.tsv` | `crates/dict/data` | 540 条中英对照，构建移动端索引时用 | 只有 540 条，且不参与候选 |
| 多语言输入（M0–M3） | `crates/{en,ja,ko,es}` | 用户**切到**那门语言后用它打字 | 不是「打中文出英文」，是另一件产品能力 |

所以真正缺的是：**中文组合态下，候选栏里出现目标语言的写法**。

## 决策

在候选层实现「目标语言候选」，数据来自离线词表：

1. `tools/build_zh_en_gloss.py` 从 CC-CEDICT（12.5 万条）生成 `crates/gloss/data/zh-en.tsv`（3 万条多字词，527 KB），按主词库词频与英文词频裁剪；
2. `Session::set_target_language("en")` 打开开关，`finish()` 在候选末尾追加最多 3 条，`comment = "EN"`；
3. 中文候选排序**完全不动**：英文只追加在末尾，分数低于对应中文候选；
4. 关闭是默认之外的一等公民：传 `""` / `"off"` 立即生效，候选随下一次按键消失；
5. 平台侧：macOS 默认打开（可 `defaults write dev.inputflow.inputmethod liana.targetLanguage off` 关闭），其余端经 `liana_set_target_language` 打开。

## 备选方案与为什么没选

### A. 离线词表 + 候选追加（采纳）

- 成本：一次数据构建（脚本已入库）+ 内核 40 行 + FFI 两个函数。
- 风险：词义质量取决于 CEDICT；词级正确、句子级仍要靠 `gloss` 的最长匹配拼接。
- 回滚：删掉 `zh-en.tsv` 并把 `target_language` 默认设为 `None`，零迁移成本。
- 为什么选它：与产品前提（本地、无服务器、离线可用）一致；延迟为零；可评测。

### B. 在线翻译 API

- 成本：低（接口现成），但每次按键都要发请求。
- 风险：断网即失效；用户输入内容离开本机——与「隐私优先」的产品前提冲突；按量计费。
- 回滚：容易，但已经建立的用户预期收不回来。
- 结论：只能作为**可选精修**，不能作为候选来源。

### C. 系统 Translation framework（Apple）

- 成本：中；要处理语言包下载状态与键盘扩展的内存上限（约 60 MB）。
- 风险：`Translation` 在键盘扩展里可用性未经实测；首次使用要下载语言包，离线首启不可用；只覆盖 Apple 平台，四端要各写一套。
- 结论：留作后续「整句精修」的候选实现，不进 M1。

## 后果

- 新增数据 527 KB（`crates/gloss/data/zh-en.tsv`），编译进内核静态库；iOS 键盘扩展的常驻内存要复测。
- 候选 JSON 多一种来源（`comment: "EN"`），各端 UI 可据此加语言角标。
- CC-CEDICT 为 **CC BY-SA 4.0**：必须在 `SOURCES.md` 署名并给出许可链接；与本项目 AGPL-3.0-only 的兼容性属法务判断，此处只记录事实，不代替法律意见。
- 词表只收多字词：单字英文释义歧义过大（好 → good/well/so），放进候选栏是噪音。

## 未决

- 句子级「中文整句 → 通顺英文」仍走 `gloss` 的最长匹配，多词拼接质量一般；要不要引入小型翻译模型，留待评测数字说话。
- 日/韩/法/德/西/俄 的词表尚未构建；CEDICT 只有中英，这些语言需要另找数据源。
