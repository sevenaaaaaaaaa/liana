# ADR-0012：整句解码加字级搭配模型

状态：已接受（2026-10-19）

## 背景

整句解码原来是纯 unigram 的 Viterbi：每个位置只保留一条最优路径，同音词只取词频最高的那个。
「你是什么时候到的」出「道德」、「我会尽快回复你」出「恢复」——不看上下文就分不出来。
个人学习（搭配加分、知你重排）只覆盖自己打过的字，新句子仍然靠词频。

## 决策

1. **数据**：用万象 LMDG 的语法模型（`wanxiang-lts-zh-hans.gram`，48GB 多领域语料训练，CC BY 4.0）。
   它是 librime-octagram 格式：键是 2～6 个字的片段，值是搭配分。`xtask lm build` 自己实现
   darts-clone 双数组遍历与 octagram 字编码解码，抽出由 6000 个常用字组成的 2～3 字片段（全部）
   与 4 字片段（分 ≥ 17.5），约 1100 万条。
2. **格式**：自有 LMC2（`crates/dict/src/lm.rs`）：键按字表下标打包成 u64、排序后每 128 条一块做差值变长编码，
   分量化成 1 字节；42MB，加载后不展开，单次查询亚微秒级。作为可选附件挂在 `Dictionary` 上，
   放在 `base.ifd` 旁边（`base.lm`），没有它时解码与原来完全一致。
3. **打分**：词与词交界处，「上文末尾 1～2 个字 + 词开头 1～2 个字」的各种拼法里，每条命中的片段贡献
   `max(0, 分 - 8)`，加总后 × 0.35 计入整句分。累加比只取最高分稳：越长的片段原始分天然越高，
   只取最高分会让一条偶然的 4 字片段压过几条一致的短片段。阈值与权重用 `xtask accuracy`
   的整句 / 困难 / 词汇三套评测调出。
4. **解码**：Viterbi 改为 beam search（每个位置 8 条，按已解码文本去重），有模型时同音词前 4 个都参与竞争；
   只对覆盖最好的前 6 条切分跑带模型的完整搜索，其余切分仍用纯词频，长输入保持流畅。
   最多给出 3 条不同的整句候选（同音的另一种说法常在第二条）。
5. **分发**：`.gram` 约 400MB，不进仓库；macOS `build.sh` 首次构建时下载到本机缓存并生成 `base.lm`，
   安装器 / `install.sh` 与 `base.ifd` 一起复制到用户数据目录。下载失败或 `LIANA_NO_LM=1` 时不带模型。

## 后果

- 日常整句评测（147 句）首选正确率 67% → 81%，前五 82% → 91%；困难集、词汇集不退步。
- 安装包增加约 42MB；输入法进程多占约 42MB 内存（进程内共享一份）。
- 80 个字母的超长输入，单键解码最坏约 13ms（原来约 6ms）；常规长度在 3ms 以内。
- 其他平台（iOS / Android / Linux / 鸿蒙 / Windows）暂不带模型，行为不变；体积敏感的移动端后续可换更小的剪枝档。
- 「的 / 得」「在 / 再」这类仍有错误：需要更长的上下文或个人学习，交给下面的长句 AI 重排。


## 补充：词级 bigram 可行性与调参实验（2026-11-14）

用户提出「把太咸/吃辣/牵手这类词与词的搭配做成压缩表，补 2 字交界模型的盲区」。先查了现有搭配模型里这些片段是否存在（`xtask lm get`）：

```
太咸 11.0   吃辣 11.0   牵手 11.1   西安 11.2
去成都 13.7  在成都 15.9  到成都 16.0  一杯水 15.8
我们明天 18.2  电脑坏了 17.9  请给我 15.7
成都（2 字键）不存在
```

也就是说这些搭配**已经在模型里**，问题不在「没有词级证据」，而在解码器如何使用它。做了三组调参（147 句整句评测，mobile-core 词库 + 5.3MB 剪枝模型）：

- 搭配权重 `LM_WEIGHT` 0.35 → 0.45/0.55/0.7/1.0、阈值 8 → 6：最好仍是 0.35/8（72%/84%），提高权重反而 70% 以下。
- 同音词扫描数 8 → 16/32、beam 8 → 16：准确率完全不变（72%/84%），只是变慢。
- 结论：单纯加强字级搭配或扩大搜索，无法让「咸」压过「现」这类高频同音字；「太咸」的搭配分只有 11（扣阈值 8 后 3 分），而 unigram 频率差就有 3.4 分左右。

**为什么直接做词级 bigram 表也帮不上**：如果词对分数仍从同一份 octagram 字片段推导（太咸=11、吃辣=11、牵手=11.1），证据强度不变，只是换了个存储形式；要真正超过字级模型，需要**语料统计的词对频率/PMI**（另外的数据源），或更大的模型（15.5MB 可达 76%，但键盘扩展内存 +27MB，风险高）。

因此本轮不新增词级 bigram 表；先保留 5.3MB 模型，并留下 `LIANA_LM_WEIGHT` / `LIANA_LM_THRESHOLD` 环境变量用于后续调参，`xtask lm get` 用于检查任意片段分数。

## 补充：长句 AI 重排（2026-10-20）

搭配模型之上再加一层可选的本机小模型（ADR-0004 的边界不变：用户自装 llama.cpp、点击下载模型、只连 127.0.0.1）。

- **何时**：首选是 6 个字以上的整句、前 5 个候选里有 2 条以上同长度整句，停顿 0.25 秒后异步发起；同一串输入只排一次，
  结果回来时输入已变就作废。同传开启时不做。设置「本地 AI › 长句 AI 重排」可关。
- **怎么打分**：`前缀 + 候选` 按模型自己的分词切成 token，逐个读「下一个 token」的 top-40 概率表取 log 概率并累加，
  各 token 请求并行（服务 `-np 4`、复用提示词缓存）。不用「语法约束强制生成」：那样模型会把「有什么」拆成单字生成，
  分数被严重低估（实测反而把对的改错）；也不用「让模型选序号」：0.5B / 1.5B 都几乎乱选。
- **何时换**：模型分数比当前首选高 3 以上才把那条提到第一（`liana_promote`，同层内换位、不改学习记录）。
- **模型**：只用 Qwen 系列（Qwen2.5 0.5B 推荐、1.5B 也可）；Gemma 270M 实测会把整句首选从 120 句降到 85 句，不启用。
  重排用独立的 llama-server 实例，空闲 5 分钟自动退出释放内存。
- **效果**（Qwen2.5 0.5B，日常整句 147 句）：首选 120 → 127 句（81% → 86%），困难集不退步；
  单次重排约 50～120 ms（服务刚启动的第一次约 1 秒），不占打字路径。1.5B 准确率相同、慢一倍。
